That's also where I've spent most of my career on the parts of e-commerce platforms customers never see directly — catalog systems, search infrastructure, pricing pipelines, and the backend plumbing that keeps millions of products indexed, priced, and discoverable.

In 2021 I moved to Rakuten Rewards to lead catalog and AI/ML integration for a fashion & home retail platform, and I'm now at Rakuten Marketing. My applied-AI work goes back further than people often assume: I started by fine-tuning classification models on AWS SageMaker, moved into LLM fine-tuning and OpenAI integration for production ranking pipelines, and most recently customized CLAUDE.md configuration and authored multiple SKILLS.md files to create reusable Claude/Cursor skills that streamlined development workflows — enabling the product team to focus on feature development. I care about systems that are boring in production — observable, well-instrumented, and easy to hand off — and I like mentoring engineers into being the kind of on-call partner you actually want at 2am.

case study

Building an AI-native development workflow

Internal Reporting Platform Spring Boot · Java · Kubernetes Claude Code · Cursor

First AI-native project on the team: built almost entirely through Claude/Cursor "vibe coding" rather than hand-written code — no prior AI-dev conventions existed before this.

Replaced per-seat BI licensing: removed a licensed BI platform's embedded reporting (billed per user, regardless of usage) with an in-house Spring Boot service.

Self-service delivery workflow: Jira ticket → AI implementation → branch-based K8s preview → developer review → production, with full deploy automation as the next milestone.

Adopted org-wide: the CLAUDE.md/SKILLS.md pattern has since been picked up by 3 other teams, extended with Slack/Teams integrations.

The Problem — why this project existed

Reporting for this platform ran entirely on a licensed BI tool, embedded into our internal application — users were redirected to a page where we hosted the header/footer, and the BI tool rendered all report content, fed by data from our big-data stores. Licensing was per-seat: if a client had 20 people using the reports, we paid for 20 licenses regardless of actual usage. As the client base grew, so did the bill, disconnected from the value we were actually delivering.

There was also no established AI-assisted development practice on the team before this — nothing shared, nothing reusable. This was the first project where the goal was to work almost entirely through AI-assisted ("vibe") coding rather than traditional hand-coding — prompting Claude and Cursor to implement changes rather than writing most of the code by hand.

Constraints — what made it hard
  • Replace a paid, embedded BI tool without losing functionality clients already depended on.
  • No prior AI-dev conventions to build on — had to define the process from zero.
  • Needed a workflow reliable enough that AI-generated code could be trusted and reviewed efficiently, not just generated quickly.
The Approach — how it works

Built the replacement as a Spring Boot/Java service, deployed initially on Cloud Run and later migrated to Kubernetes as it matured.

The larger goal was a self-service development workflow: a user submits a Jira ticket describing the change they want. Claude or Cursor implements it. The branch deploys automatically to a dedicated, branch-based deployment pod on Kubernetes so the requester can review the result directly — no need to wait for a full release cycle to see it working. Once they're satisfied, a developer (me) reviews the code and promotes it to production.

CLAUDE.md and a set of SKILLS.md files are the foundation making this trustworthy: repo-wide context, layer-by-layer conventions, and two structured skills — one scaffolds a full new feature end-to-end (ticket → implementation → automated code review → commit/PR), the other handles the far more common case of adding a parameter to an existing endpoint. Both let a requester choose their depth of involvement, from plain-English descriptions to exact class-level specs.

Outcome — what happened

The service replaced the BI platform's core reporting function. The CLAUDE.md/SKILLS.md pattern was adopted organically by three other teams, who've extended it with skills integrating into Slack and Teams. The branch-per-ticket review workflow is live; full production auto-deployment is the next milestone.

Retrospective — what I'd tell someone starting this today

The biggest shift in how I think about this work: prompting is the actual skill, not a shortcut around one. Early on I treated the CLAUDE.md/SKILLS.md files as documentation — write it once, done. What I've learned is that a skill is only as good as the prompt driving it; the same SKILLS.md file produces very different output depending on how precisely the request is framed. The tiered-depth approach (plain English vs. exact class names) exists because of this — an admission that vague prompts need more AI judgment calls, which means more risk, so the workflow makes that tradeoff explicit rather than assuming one prompting style fits everyone.

AI-generated code isn't always ship-ready. It hallucinates — confidently generating code that references methods, patterns, or conventions that don't actually exist in the codebase. That's exactly why review isn't optional in this workflow; every AI-authored change gets reviewed by a developer before reaching production, and that review has caught real issues, not just style nits.
Context size is a real, recurring constraint. On a codebase this size, how much relevant context fits in the window directly affects output quality — too little and the AI misses established patterns; too much and signal gets diluted. This is part of why CLAUDE.md points to smaller, focused rule files instead of one giant document — right-sizing what gets loaded per task, rather than assuming more context is always better.
