01 · Product classification & catalog ingestionRakuten Rewards / ShopStyle & Collective Voice · 2021–2025

The problem

Product feeds from different merchants needed normalization and consistent categorization so products could be organized and discovered across fashion and home retail.

My contribution

I designed and built a custom SageMaker classification pipeline and a human-in-the-loop correction system. I also designed a Java microservices framework to ingest, normalize and process catalog data.

Design & iteration

The model was retrained weekly on refreshed catalog data. Human corrections fed into retraining cycles. I subsequently contributed to replacing legacy custom models with GPT-4 to improve classification and reduce model maintenance.

Outcome & scope

The SageMaker work improved classification accuracy from 60% to 92%. The related ingestion framework processed 500M+ SKUs across 1,000+ merchant feeds; these figures describe ingestion scope, not model evaluation sample size.

Engineering decisions

DecisionPurpose & implication
Human corrections alongside model predictionsProvide a correction path that feeds future retraining. Model output alone is not the end of the workflow.
Weekly retraining on refreshed dataBring updated catalog data into the model on a recurring schedule.
Transition toward GPT-4Address custom-model maintenance overhead. My contribution was part of a broader migration effort.

Transferable strengths: Normalizing heterogeneous data, integrating model predictions and maintaining a human correction workflow.

Engineering focus: Feed normalization, repeatable retraining and a human correction loop. The later GPT-4 transition addressed the ongoing maintenance burden of custom models.

02 · AI-assisted reporting platformRakuten Marketing · 2026

The problem

Embedded reporting depended on a BI tool with per-seat licensing. Costs grew with the user base, and the team had no shared conventions for AI-assisted feature delivery.

My contribution

I built the replacement Spring Boot service using Claude and Cursor, authored repository context and reusable development skills, and established a branch-based preview and developer review workflow.

Design decisions

Repository context points to focused rule files. Separate skills support full feature implementation and smaller endpoint changes. Dedicated Kubernetes previews let requesters review changes before production promotion.

Outcome

The service replaced the BI platform’s core reporting function. Three additional teams adopted the context-and-skills pattern and extended it with Slack and Teams integrations.

Engineering decisions

DecisionPurpose & tradeoff
Focused repository rule filesLoad relevant conventions without relying on one large context document. Context selection remains part of the engineering work.
Branch-specific previewsLet requesters inspect a working change before a release. The preview is a review surface, not a substitute for code review.
Developer review before promotionCatch nonexistent methods and mismatched conventions in generated code. Delivery still depends on accountable human judgment.

Transferable strengths: Replacing licensed software, integrating enterprise workflows and establishing repeatable delivery with human review.

Live: Branch previews and developer review. Next milestone: Fully automated production deployment.

What I learned

AI-generated code can reference nonexistent methods or miss established conventions. Developer review has caught these issues; generated output still needs engineering ownership.

The practical tradeoff

Too little context misses important patterns; too much dilutes the signal. Focused rule files and requests with an explicit level of detail help make that tradeoff manageable.

Engineering notes

Lessons from the work.

Practical considerations behind classification systems and AI-assisted delivery.

Human feedback is part of the classification systemApplied ML · Catalog data · 2-minute read

Product classification has to deal with inconsistent merchant language. A category label can be plausible and still be wrong for the catalog taxonomy. A useful system therefore needs a way to correct predictions and carry those corrections into future iterations.

Keep the correction path explicit

In the SageMaker project described above, human corrections fed recurring retraining. The broader design lesson is to treat feedback as an input with its own quality requirements: what was corrected, which category was intended, and which version of the taxonomy applied?

Separate scale from evaluation

Ingestion volume answers how much data a platform handles. It does not establish how a classifier was evaluated. A classification result should be accompanied by the evaluation period, dataset definition and metric. For a changing catalog, looking at results by category and merchant can reveal failures that an overall accuracy number conceals.

Plan for change

Retraining and taxonomy changes solve different problems. New product language may require better examples; a new business category may require a taxonomy update. Keeping those decisions separate makes it easier to understand why a result changed.

A human feedback loop is most useful when corrections can be traced through to a later model evaluation. The target is a repeatable improvement process, with evidence for each iteration.

AI-generated backend code still needs engineering ownershipDeveloper tooling · Code review · 2-minute read

Generating a working change is only one part of delivery. A backend change also needs to fit existing contracts, data access rules and operational expectations. A preview can demonstrate behavior while leaving important questions unanswered.

Give the tool focused context

The reporting workflow uses repository context and smaller rule files for recurring tasks. This keeps conventions close to the work. A full feature and a new endpoint parameter do not need identical instructions or the same amount of context.

Review the assumptions

The supplied project retrospective describes AI output that referenced nonexistent methods or mismatched conventions. Review should check those assumptions directly. For backend changes, I would also ask: does the endpoint preserve its contract, validate its inputs, enforce the intended access controls, and handle failures clearly?

Separate preview approval from code approval

A requester can verify whether a feature meets the need. A developer must assess whether the implementation is suitable for the codebase. The reporting workflow preserves both steps before production promotion.

Useful evaluation of an AI-assisted workflow should include review effort and defect outcomes alongside implementation time. Faster generation is valuable when the team can still explain, maintain and operate the resulting system.
